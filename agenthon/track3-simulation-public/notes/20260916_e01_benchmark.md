# E01 Scalar Latency Clip Benchmark Plan

## Experiment

E01 replaces the scalar `np.clip` call in `ScenarioLatencyModel.get_latency`
with scalar comparisons. The experiment is isolated on:

```text
branch: exp/t3-scalar-latency-clip
commit: 5548dc2
control commit: 8187954
```

The focused latency-model tests pass. Fixed-seed AS01 and AS06 checks also
produced exactly matching event traces and message traces, including values,
row order, dtypes, counts, and hashes.

## Objective and primary metric

Measure E01 against the candidate control with the repository's local developer
harness, [`throughput/timer.py`](../throughput/timer.py). The primary metric is:

```text
median_events_per_sec
```

The harness calculates each run's throughput from the event parquet row count
and host-measured whole-container wall-clock time:

```text
run_events_per_sec = parquet_event_row_count / host_wall_clock_sec
```

The simulator's self-reported `events_per_sec` in `events.json` is diagnostic and
must not be used as the experiment result.

## Controlled setup

For both control and E01, use:

- the same host and Docker runtime;
- the same scenario files and timer-derived seed families;
- 4 CPUs and 16 GB of memory;
- 5 total runs per scenario;
- the first run discarded as warm-up;
- the median of the remaining 4 runs;
- unprofiled execution.

Benchmark both public scenarios:

- AS01 (`as01_base_mix.json`) as the smaller representative workload;
- AS06 (`as06_throughput_fast.json`) as the main local throughput indicator.

The public scenarios provide directional local evidence. The official ranking is
measured by the organizer's runner on sealed scenarios.

## Comparison

Calculate the result independently for AS01 and AS06:

```text
speedup = E01.median_events_per_sec / control.median_events_per_sec
improvement_percent = (speedup - 1) * 100
```

Record the following from each `throughput.json` file:

- `median_events_per_sec`;
- `raw_events_per_sec`;
- `wall_clock_seconds`;
- `std_events_per_sec`;
- `seed_family`;
- `warmup_discarded`.

Use the raw scored-run distribution and standard deviation to judge whether the
median difference is larger than ordinary run-to-run noise.

## Repeatability check

If Run 1 indicates a useful improvement, perform a second batch with the order
reversed: run E01 first and control second. Save it under `run02` without
overwriting Run 1:

```text
out/control/benchmark/run02/{as01,as06}/throughput.json
out/E01_scalar_latency_clip/benchmark/run02/{as01,as06}/throughput.json
```

Reversing the order helps reveal systematic warm-cache, temperature, or host-load
bias. Keep E01 only when the improvement is repeatable and remains meaningful
relative to the observed variance, with correctness still passing. Otherwise,
record E01 as neutral or rejected rather than relying on a single favorable
median.

## Executed results — 2026-09-16

Both batches used matching seed families and discarded their first run. The
table compares the timer's median over the four scored runs in each batch.

| Scenario | Batch | Control median (events/s) | E01 median (events/s) | Speedup | Improvement | Median seed-paired ratio |
|---|---:|---:|---:|---:|---:|---:|
| AS01 | Run 1 | 5,816.72 | 6,206.14 | 1.066947x | +6.69% | 1.055646x |
| AS01 | Run 2 | 5,769.49 | 6,074.06 | 1.052788x | +5.28% | 1.067524x |
| AS06 | Run 1 | 7,591.36 | 8,152.06 | 1.073860x | +7.39% | 1.071473x |
| AS06 | Run 2 | 7,706.38 | 8,088.80 | 1.049624x | +4.96% | 1.055198x |

As a supplementary aggregate, pooling the eight scored rates per image gives:

| Scenario | Control median (events/s) | E01 median (events/s) | Median speedup | Median of all seed-paired ratios |
|---|---:|---:|---:|---:|
| AS01 | 5,791.00 | 6,159.02 | 1.063550x (+6.36%) | 1.067524x (+6.75%) |
| AS06 | 7,664.31 | 8,132.81 | 1.061127x (+6.11%) | 1.057917x (+5.79%) |

The experiment improved the primary metric in both scenarios and in both batch
orders. All eight scored AS06 seed-paired ratios favored E01; they ranged from
1.010470x to 1.095451x. This supports keeping E01 as a measured optimization.
