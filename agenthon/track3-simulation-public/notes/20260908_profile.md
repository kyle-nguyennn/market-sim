## Executive summary

Profile the simulator inside the baseline Docker image to use the same pinned Python
dependencies and patched ABIDES engine as regression runs. No host Python or ABIDES
installation is needed. Keep each scenario/settings run in its own folder under
`out/`; the baseline AS01 run uses `out/baseline_as01/`.

## Plan

### Build the Docker images

Run all commands from the `track3-simulation-public` repository root. Build the
baseline image, then add py-spy in a separate profiling image:

```bash
docker build --platform=linux/amd64 \
    -t track3-abides-baseline:latest baselines/

docker build --platform=linux/amd64 -t track3-abides-profile:latest - <<'EOF'
FROM track3-abides-baseline:latest
RUN python -m pip install --no-deps py-spy==0.4.2
EOF
```

Rebuild both images after changing the baseline adapter or engine patches. The
container runs the code baked into the image.

### Profile with py-spy

Use a descriptive run name for each scenario and settings combination, such as
`baseline_as01`, `baseline_as02`, or `baseline_as01_cpu2`. Use a new suffix for
repeated measurements you want to retain; reusing a folder overwrites its outputs.
Update `scenario_file` and the Docker resource options to match the run name.

```bash
run_name=baseline_as01
scenario_file=as01_base_mix.json
mkdir -p "out/$run_name"

docker run --rm \
    --cap-add SYS_PTRACE \
    --network none \
    --cpus 4 \
    --memory 16g \
    -v "$PWD/regression_suite/scenarios:/input:ro" \
    -v "$PWD/out/$run_name:/output" \
    track3-abides-profile:latest \
    py-spy record -o /output/profile.svg \
    -- python -m abides_fork.simulate \
       --config "/input/$scenario_file" \
       --out /output/trace.parquet
```

`SYS_PTRACE` permits py-spy to inspect the Python process inside Docker; see the
[py-spy Docker instructions](https://github.com/benfred/py-spy#how-do-i-run-py-spy-in-docker).
The image already sets `PYTHONPATH=/opt` for the adapter.

This run writes the following files on the host:

```text
out/baseline_as01/
├── profile.svg
├── trace.parquet
├── message_trace.parquet
└── events.json
```

Confirm the simulator prints its final JSON metadata and exits without a traceback.
py-spy's `Errors: 0` counts sampling errors; it does not establish simulation
success or correctness. Use the regression harness separately to check correctness.

Open `out/baseline_as01/profile.svg` in a browser. py-spy samples the full process,
including imports, configuration, and trace writing; `wall_clock_sec` in
`events.json` measures the simulation loop only. A few hundred samples can reveal
broad hotspots, but use a longer scenario for finer comparisons. Profiled timings
are diagnostic measurements, not official throughput results.

You are looking for broad regions such as:
```
Kernel.runner
├── heapq.heappop / heappush
├── Agent.receive_message
├── TradingAgent.receive_message
├── ExchangeAgent.receive_message
│   └── OrderBook...
├── latency_model.get_latency
├── random_state.*
└── logging / trace construction
```
The width of each stack tells you roughly where CPU time is going.
The first question is simply: What are the top 5 stacks by CPU time? That alone will likely eliminate several wrong optimization ideas.

### Deterministic profiling for call counts with cProfile

cProfile is included in the original baseline image and does not need
`SYS_PTRACE`. Give it a separate run folder so its simulation metadata and traces
do not overwrite the py-spy run:

```bash
run_name=baseline_as01_cprofile
scenario_file=as01_base_mix.json
mkdir -p "out/$run_name"

docker run --rm \
    --network none \
    --cpus 4 \
    --memory 16g \
    -v "$PWD/regression_suite/scenarios:/input:ro" \
    -v "$PWD/out/$run_name:/output" \
    track3-abides-baseline:latest \
    python -m cProfile -o /output/t3.prof \
    -m abides_fork.simulate \
    --config "/input/$scenario_file" \
    --out /output/trace.parquet
```

Inspect the saved profile using the same image's Python version:

```bash
docker run --rm -it \
    --network none \
    -v "$PWD/out/baseline_as01_cprofile:/output:ro" \
    track3-abides-baseline:latest \
    python -m pstats /output/t3.prof
```
Inside:
```
sort cumulative
stats 40
```
I care about both `tottime` and `cumtime` because they answer different questions.
If you see:
```text
function                         calls       tottime     cumtime
----------------------------------------------------------------
heapq.heappop                    1,200,000   2.1s        2.1s
Kernel.send_message              800,000     1.8s        5.7s
ExchangeAgent.receive_message    300,000     1.2s        9.4s
OrderBook.handle_limit_order     150,000     4.8s        7.1s
...
```
Then you start building a cost model.
The decomposition we want is approximately:

$$
\begin{aligned}
T ={}& T_{\text{scheduler}}
     + T_{\text{dispatch}}
     + T_{\text{agent}}
     + T_{\text{latency}} \\
    &+ T_{\text{exchange}}
     + T_{\text{LOB}}
     + T_{\text{logging}}.
\end{aligned}
$$

That is much more useful than profiling individual functions in isolation.

### Profile by event type
For T3, aggregate profiling isn't enough.
Suppose `ExchangeAgent.receive_message()` is expensive. That function handles multiple semantic paths:
```text
LIMIT_ORDER
MARKET_ORDER
CANCEL
REPLACE
SPREAD_QUERY
...
```

You need:

$$
\boxed{
\text{cost/event type}
=
\frac{\text{total CPU for event type}}
     {\text{number of events of that type}}
}
$$

For example:
```text
SPREAD_QUERY       45%
LIMIT_ORDER        25%
CANCEL             12%
FILL response       8%
WAKEUP              5%
other               5%
```
If spread queries dominate because every agent does
```
wake
→ QuerySpread
→ latency
→ exchange
→ response
→ latency
→ agent
```
then replacing only the LOB won't attack the dominant cost.
That is precisely the kind of ABIDES overhead I suspect could matter.
